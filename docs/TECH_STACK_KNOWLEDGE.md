## 1. Python 与工程基础

### 1.1 Python 的运行模型

Python 是动态类型语言：变量绑定对象，类型属于对象，运行时决定很多行为。类型注解能提高可读性并供静态检查器、框架读取，但不会自动对所有赋值和函数调用进行强制校验。

CPython 通常把源代码编译为字节码，再由解释器执行。它适合业务编排、网络调用和数据处理；重计算往往交给底层扩展、模型服务或独立进程。动态语言不等于不需要类型设计，接口参数、数据结构和错误类型仍应明确。

### 1.2 模块、包与 src 布局

模块通常对应一个 Python 文件，包用于组织模块。import 依据 sys.path 搜索，PYTHONPATH 可以补充搜索路径。src 布局将应用源码与测试、配置、文档分离，有助于避免从仓库根目录偶然导入错误模块。

要区分三种路径：模块导入路径、当前工作目录、实际文件路径。程序可以成功 import，但仍因相对文件路径而找不到配置。使用 pathlib 与明确的项目根路径能减少这种差异。

包管理与导入也不完全同名，例如发行包 rank-bm25 的导入名称为 rank_bm25；PyYAML 的导入名称为 yaml。

### 1.3 类型注解与数据类

类型注解描述参数、返回值和容器元素类型，例如 list[str]、dict[str, float]、str | None。可选类型意味着允许缺失，需要显式处理 None。

dataclass 可以根据字段生成初始化、比较和表示方法，适合配置记录、模型描述和不可变值对象。它主要减少样板代码，不等于 Pydantic 的解析与校验能力。需要外部输入验证时，应增加校验逻辑或使用验证框架。

### 1.4 装饰器与中间件

装饰器接收函数或类，返回增强后的对象，可以增加日志、校验、注册和监控。它把横切逻辑集中管理，避免每个业务函数重复编写。

中间件通常提供 before、after 或 wrap 机制。wrap 可以在调用前后记录耗时并捕获异常。设计时要保留原函数参数、返回契约和异常语义，避免把业务失败误报为成功。

### 1.5 生成器与迭代器

生成器用 yield 逐次产出结果，保留暂停位置，适合大数据迭代和增量输出。它具有惰性：只有调用方继续迭代，后续代码才会执行。

生成器与网络流式传输不是同一个概念。若生成器只在模型完成后产出整段文本，就没有逐 token 输出。消费者提前退出也可能影响清理，需要用 finally 或上下文管理器释放资源。

### 1.6 异常处理与资源管理

try/except 用于区分可恢复失败与不可恢复失败；finally 用于保证关闭连接、清理上下文等动作。不要用过宽的 except 把所有错误都吞掉，否则配置错误、程序错误和网络异常会被混为一谈。

with 语句通过上下文管理器规定资源进入与退出过程。数据库连接、文件和网络客户端应有明确生命周期。正常结束提交事务，异常结束回滚，是常见模式；具体行为由上下文管理器实现决定。

### 1.7 ContextVar、线程局部与共享状态

全局变量被同一进程中的请求共享，不适合保存“当前请求用户”。ContextVar 将值绑定到执行上下文，适合传递请求 ID、身份和追踪信息。[Python 官方资料](https://docs.python.org/3/library/contextvars.html)

ContextVar 不是全局同步机制。上下文复制后，子上下文可以读取复制时的值，但修改未必回传父上下文；新线程也不能假设自动获得所有上下文。可靠代码应明确设置、传播与 reset 的位置。

Lock 保证一个线程进入临界区；RLock 允许同一线程重复获取。它们只保护同一进程中的共享对象，不能解决多进程和多机器一致性。锁也不能修复错误的状态作用域：按用户保存的状态仍可能被该用户两个并行会话争用。

### 1.8 GIL、同步、异步与进程

常见 CPython 构建中的 GIL 限制多个线程同时执行 Python 字节码。线程仍适合网络等 I/O 等待；CPU 密集工作可考虑进程、底层扩展或专门计算服务。不要把 GIL 当作业务数据线程安全的保证。

async/await 是协作式并发，依赖等待时主动让出控制权。async 函数里调用同步网络客户端仍会阻塞事件循环。选择同步或异步应依据调用链和依赖，而不是仅修改函数声明。

## 2. 大语言模型基础

### 2.1 LLM 与条件生成

大语言模型通常学习给定上下文后的 token 条件分布，并逐步生成输出。它能形成语言和知识模式，但生成流畅不代表事实正确。工具和外部检索是补充信息与执行能力的方式，不会改变模型权重。

自回归生成可写为：

~~~text
P(y | x) = ∏ P(y_t | x, y_1, ..., y_(t-1))
~~~

x 是输入上下文，y 是输出序列。不同 token 的选择会改变后续上下文，因此同一问题可能产生不同答案。

### 2.2 Transformer、Attention 与位置

Transformer 使用注意力机制建立 token 间联系。Q、K、V 分别表示查询、键和值；缩放点积注意力的经典形式为：

~~~text
Attention(Q,K,V) = softmax(QKᵀ / √d_k)V
~~~

多头注意力让模型在不同表示子空间学习关系；位置编码使模型能表达顺序。理解这些原理有助于解释上下文能力，但调用云模型不等于实现或训练了 Transformer。

### 2.3 Token、上下文窗口与预算

Token 是分词器产生的单位，可能是单词、子词、汉字或符号组合。字符数、字数和 token 数没有固定一一对应关系。

上下文通常包含系统提示、工具说明、历史消息、当前问题、检索资料和输出预算。上下文窗口很大也不能保证模型充分利用每段资料，噪声和位置仍会影响效果。

可采用 token 预算为各部分分配上限，优先保留系统约束、当前任务和必要证据。仅增加历史长度可能提高费用、延迟和干扰。

### 2.4 采样与生成参数

- temperature：调整采样分布，较低值一般更集中，但不是事实正确性的开关。
- top_p：保留累计概率达到阈值的候选 token，属于核采样。
- max_tokens 或同类参数：限制最大输出，不直接限制整段任务总费用。
- stop：指定停止模式，具体支持与语义依模型接口而定。
- seed：部分服务提供可重复采样控制，但不能保证跨版本、跨硬件或所有服务完全确定。

调参时先明确任务：抽取、计算和格式输出偏重稳定；创作偏重多样性。提高准确性通常更依赖证据与验证，而非单独降低 temperature。

### 2.5 幻觉与不确定性

幻觉包括编造事实、来源、数字，或给出与证据不一致的结论。常见原因是知识缺失、问题歧义、错误召回、无关上下文和缺少输出验证。

缓解方式包括检索、限定证据、结构化输出、引用验证、计算交给确定性工具和允许拒答。模型自报的“置信度 95%”不是经过统计校准的正确概率。

### 2.6 训练、微调、提示与 RAG 的区别

训练和微调改变权重；提示工程改变当前输入；RAG 在回答时补充外部资料。它们解决的问题不同：微调常用于行为、格式和领域任务适配，RAG 更适合持续更新、可引用的知识。

不应通过微调替代频繁变化知识的检索，也不应认为 RAG 可以替代模型所有能力学习。LoRA 是低秩参数适配方法，属于延伸知识，并非云 API 调用天然具备的功能。

## 3. 模型服务、模型路由与可靠调用

### 3.1 云模型 API 与 SDK

模型服务通过 HTTP 接口提供推理，SDK 封装认证、请求结构、响应解析和部分异常。DashScope 是此类服务接口；ChatTongyi 与 DashScopeEmbeddings 是接入 LangChain 抽象的包装器。

包装器统一接口，但不能消除供应商差异：工具调用、流式事件、上下文上限、参数名称、权限和计费方式可能不同。更换供应商需要实际适配与契约测试。

### 3.2 模型工厂、注册表与路由

工厂负责根据配置创建实例，注册表记录模型名称、供应商、用途、启用状态和凭证位置。路由依据规则选择模型，常见规则包括优先级、费用、响应时间、任务难度和可用性。

模型可用性应分层理解：有配置 → 有凭证 → 认证通过 → 有模型权限 → 网络可达 → 请求成功 → 输出符合任务要求。仅检测环境变量非空只覆盖前几步中的很小部分。

### 3.3 Retry、Fallback 与 Circuit Breaker

- Retry：同一操作暂时失败后重试，适合短暂网络异常和部分限流。
- Fallback：换另一个模型、供应商或降级策略。
- Circuit Breaker：连续失败后暂时停止调用，经过冷却或探测后恢复，防止故障扩散。

指数退避常为 delay=min(cap, base×2^attempt)，再加入 jitter 随机抖动，避免大量客户端同时重试。服务返回 Retry-After 时应纳入策略。

Tenacity 提供重试装饰器、等待策略、停止条件和重试异常过滤。安装该库并不等于自动启用了重试；必须明确包裹哪些操作、最多几次以及总时间预算。

### 3.4 限流、额度与费用

限流通常约束单位时间内请求数或 token 数；额度通常约束总量、账户预算或授权；免费额度是供应商商业策略的一部分。三者不能仅凭错误字符串视为同一原因。

严格费用控制需要同时记录输入与输出用量、实际模型、价格或供应商账单、任务预算和余额策略。同一供应商下多个模型可能共享账户预算，换模型未必恢复。

~~~text
估算成本 ≈ 输入 token 数 × 输入单价
         + 输出 token 数 × 输出单价
         + Embedding、Rerank、搜索等附加成本
~~~

具体价格与免费政策会变化，应以供应商当前账单和控制台为准。模型错误回退不是免费余额查询，也不是保证不收费的机制。

### 3.5 幂等与任务重放

纯查询重试通常风险较小；写入任务、发送信息、扣款等操作可能产生重复副作用。幂等性意味着相同逻辑操作执行多次，最终效果与执行一次一致。

常见办法是幂等键、数据库唯一约束、保存已执行结果和状态机。若整个 Agent 任务重放，要知道哪些工具已完成，并复用结果，而非再次执行所有写操作。

## 4. LangChain 与 LCEL

### 4.1 LangChain 的抽象

LangChain 为模型应用提供统一的模型、消息、工具、提示、文档、检索器和运行接口。抽象的价值是组合和替换组件，但适配器仍可能有行为差异。

LangChain Core 提供基础抽象；Community 提供第三方集成；独立集成包承载特定组件。理解这三层有助于定位升级冲突：框架 API、集成包装器与供应商 API 可能分别发生变化。

### 4.2 消息、Document 与输出解析

- 消息表示对话角色与内容，包括系统、用户、AI 和工具消息；部分消息还带工具调用和使用量。
- Document 表示正文与 metadata，元数据可以保存来源、页码、标题、权限和块标识。
- 输出解析器把模型返回转换成所需形式。StrOutputParser 提取字符串，不校验事实正确性或业务字段完整性。

结构化输出可配合 Pydantic 模型验证字段，但通过字段校验也不等于通过事实核验。

### 4.3 PromptTemplate

PromptTemplate 将固定文本与输入变量分离，避免手动拼接混乱。变量必须明确，例如问题、资料、格式要求。外部资料插入模板时仍是不可信输入，模板本身不会自动清除注入。

模板加载后要考虑版本、缓存和热更新策略。修改文件不保证已经创建的实例立即使用新内容。

### 4.4 LCEL 与 Runnable

LCEL 是 LangChain Expression Language，通过可运行组件组合表达调用链。管道符用于将前一阶段结果交给后一阶段：

~~~text
PromptTemplate | 模型 | 输出解析器
~~~

Runnable 通常提供 invoke、batch、stream 及对应异步接口。链式表达明确数据流，便于替换组件与插入日志，但复杂条件分支和持久状态更适合图式编排。

### 4.5 Chain 与 Agent

Chain 的流程通常预先固定；Agent 根据模型输出选择工具和下一步。固定抽取、格式转换适合 Chain；需要不确定次数的信息获取与决策适合 Agent。

引入 Agent 会增加不可预测性、延迟与工具误调用风险。因此确定性业务规则应保留在代码层，不必把所有流程都交给模型。

## 5. LangGraph 与有状态执行

### 5.1 State、Node、Edge 与 Reducer

State 是运行状态；Node 读取状态并产生更新；Edge 表示执行关系；条件边根据状态选择下一步。Reducer 定义多个更新如何合并，例如消息追加而非简单覆盖。

图结构能明确分支、循环、等待和终止条件。状态字段要有清晰含义，避免把长期业务数据、短期消息和临时工具结果混成一个不可维护的大对象。

### 5.2 create_agent 与 LangGraph

LangChain create_agent 将模型、工具和中间件组装为 Agent 运行循环，使用 LangGraph 支撑状态执行。理解其底层图机制有助于调试，但调用构造器不等于亲自实现了任意复杂工作流。[官方 Agents 文档](https://docs.langchain.com/oss/python/langchain/agents)

### 5.3 Checkpoint、Thread 与持久化

Checkpoint 是某个执行点的状态快照；Thread 是一组相关执行状态的标识。它们支持跨轮对话读取历史状态，并为恢复和人工介入提供基础。[官方 Persistence 文档](https://docs.langchain.com/oss/python/langgraph/persistence)

MemorySaver 使用内存，进程退出后状态消失；SqliteSaver 将检查点持久化到 SQLite。业务会话表、聊天展示记录、检查点和长期记忆具有不同职责，不应互相替代。

### 5.4 持久化与可靠恢复

保存状态只是恢复的前提。可靠恢复还要处理：外部副作用是否已执行、模型结果是否可复用、检查点提交与业务写入是否一致、并发请求是否顺序化以及失败后的重入语义。

人工中断与恢复通常还需要明确审批点、恢复输入和拒绝路径。不能仅因为有检查点就声称支持完整 Human-in-the-Loop。

### 5.5 流式模式与执行限制

状态快照流、状态更新流、消息 token 流和自定义事件流传递的内容不同。选择流式模式前应明确接收方需要状态变化还是文本片段。

递归或步数上限限制图运行步数，防止无限循环；还应单独考虑时间、模型调用次数、工具次数、token 和费用限制。步数上限不能代替全部资源预算。

## 6. Agent、ReAct 与工具调用

### 6.1 Agent 的组成

Agent 可以概括为模型、任务约束、工具、状态与执行循环。模型选择行动，程序执行工具并把结果交回模型，循环直到得到答案、达到上限或遇到终止条件。

自主性越强，越需要权限、预算、观察和终止机制。Agent 是架构模式，不意味着系统能可靠处理任何任务。

### 6.2 ReAct

ReAct 将推理决策与行动观察交替进行。工具查询得到的信息会影响下一步决策，比一次性猜测更适合需要外部事实的任务。

理解 ReAct 的重点是“依据观察调整行动”，不需要暴露模型内部思维链。用户可看到行动与证据摘要，而非隐藏推理内容。

### 6.3 Tool Calling 与 Schema

工具调用包含工具名称、参数和调用 ID。函数签名、类型注解和说明可以构成参数 Schema；模型输出调用意图，执行器负责真正运行。

工具返回需要与调用 ID 对应，否则模型无法正确关联观察。JSON Schema 描述输入结构，但实际业务权限、日期有效性和资源上限仍需执行代码检查。

### 6.4 工具契约

可靠工具接口应描述用途、输入限制、成功输出、失败类别、是否可重试和是否有副作用。结构化结果比混合自然语言更容易检测失败。

~~~json
{
  "status": "error",
  "error_code": "UPSTREAM_TIMEOUT",
  "retryable": true,
  "data": null
}
~~~

以上是契约设计示例，不是对现有所有工具返回格式的声明。执行无异常、供应商成功和用户任务完成是三个不同指标。

### 6.5 Planning、Workflow 与 Multi-Agent

Planning 是把目标分解成子任务；Workflow 是预定义执行规则；Multi-Agent 是多个具备独立职责或状态的 Agent 协作。它们不等同于一个 Agent 调用多个函数。

多 Agent 的价值可能来自职责分工、隔离和交叉检查，但会增加通信成本、协调难度和错误传播。应先证明单 Agent 的瓶颈，再引入更多 Agent。

### 6.6 短期记忆与长期记忆

短期记忆通常是当前任务或会话的消息状态；长期记忆是跨会话保存的偏好、事实与经历。长期记忆还需要来源、版本、有效期、纠错、删除和冲突处理。

把全部聊天存进数据库不等于建立高质量记忆系统。必须决定哪些信息值得保存、如何检索、何时遗忘以及如何避免把错误结论写成事实。

<a id="k07"></a>
## 7. 提示词工程与 Skill

### 7.1 提示词的基本组成

提示通常包括角色、目标、输入边界、执行规则、证据要求、输出格式和缺失信息处理。清晰约束比“尽量准确”“请专业回答”更可检验。

例如证据要求应明确：数字和日期来自哪里；哪些信息允许推断；无法验证时如何表达；输出中如何标注引用。格式要求应明确字段、单位和禁止补造的信息。

### 7.2 消息层级与动态提示

系统消息描述高优先级行为规则，用户消息描述任务，工具和检索结果提供数据。层级是模型协议与行为设计的一部分，但不是不可突破的安全证明。

动态提示可根据任务切换方法与格式。更稳定的设计是保留不可替换的基础规则，再附加领域方法与任务信息，避免整个系统提示被专项模板覆盖。

### 7.3 Skill 的技术含义

Skill 是可复用的任务方法、提示、约束和可能关联的资源。它侧重组织处理过程；Tool 侧重执行原子动作。文本模板型 Skill 与包含代码、依赖、资源和验证流程的完整技能包是不同层次。

Skill 名称应使用白名单映射到可信资源，不应允许外部输入直接拼接任意文件路径或系统指令。

### 7.4 Few-shot 与结构化输出

Few-shot 通过少量输入输出示例说明预期模式，适合格式、分类和领域表达。示例必须覆盖边界与反例，否则模型可能只模仿表面格式。

结构化输出约束字段与类型，便于程序校验。它解决“格式能否解析”，事实验证、权限与逻辑正确性仍需额外机制。

### 7.5 提示版本与实验

提示应版本化，记录适用模型和评测结果。变更时固定模型、测试集与其他参数，对比正确率、拒答、格式和成本，避免把偶然采样差异当作提升。

把资料明确标成数据能降低注入风险，但分隔符不是不可伪造的权限边界。真正有副作用的动作必须由程序层限制。

## 8. RAG 总体原理

### 8.1 什么是 RAG

RAG 是 Retrieval-Augmented Generation，即检索增强生成。在生成答案前检索外部资料，将选中的证据加入上下文，再让语言模型基于证据回答。

它把知识存储与模型权重分离，适合私有知识、更新较快的信息和需要引用来源的问答。资料仍需解析、索引、授权和维护；RAG 不会自动让脏数据变正确。

### 8.2 离线入库与在线查询

离线链路通常是：采集 → 解析 → 清洗 → 切分 → 元数据 → 编码 → 索引 → 版本记录。

在线链路通常是：问题处理 → 权限与作用域 → 候选召回 → 融合 → 重排 → 证据筛选 → 生成 → 验证与引用。

离线与在线的参数有关联：切分方式影响召回，元数据决定过滤和引用，Embedding 版本决定查询与文档是否处于同一空间。

### 8.3 召回、精排与生成的职责

召回尽量找全候选，精排从候选中优先选真正相关文本，生成把证据组织为答案。召回缺失的文档，精排无法凭空补回；资料中没有的事实，生成不应补造。

排障应按这三个阶段拆开：没有找到资料、找到了但排错、证据正确但回答错误。只更换更强聊天模型未必修复召回问题。

### 8.4 多轮问题与检索输入

“它的优点是什么”需要结合前文确定“它”指什么。只对当前问题做独立检索，会丢失指代信息。

Query Rewrite 将对话问题转换为可独立检索的问题；查询扩展增加相关术语；HyDE 生成假设性文档再做向量检索。它们属于可选方法，有额外费用与引入错误信息的风险，必须评测后采用。

### 8.5 RAG 的常见限制

- 解析不完整：扫描 PDF、表格和跨页段落丢失信息。
- 切分不合理：结论与条件被拆开，或块太大混入无关内容。
- 召回错误：同义词、缩写、版本号和精确实体处理不足。
- 权限错误：先检索后过滤，或缓存缺少身份作用域。
- 上下文错误：重复、过时或冲突资料影响生成。
- 生成错误：模型忽略证据、错误引用或过度推断。

RAG 是可拆解优化的系统，不是单个“向量搜索”函数。

## 9. 文档解析与文本切分

### 9.1 TXT、Markdown 与 PDF

TXT 解析涉及字符编码、换行与空白。Markdown 还包含标题、列表、代码块、链接和表格结构。PDF 主要保存页面布局，文本读取顺序可能与视觉顺序不同。

TextLoader 是文本加载抽象；PyPDFLoader 通常依赖 pypdf 提取 PDF 文本。扫描件若只有图片，需要 OCR；不能把 PDF 文件能打开理解为文字能被正确提取。

表格解析要保留列名、单位和行关系；代码解析应避免拆散函数与依赖。不同文档不一定适用同一种切分器。

### 9.2 Document 与元数据

正文承载知识，元数据承载来源和管理信息。常见字段包括 source_path、页码、标题层级、chunk_id、文档版本、更新时间、语料范围与权限。

元数据用于过滤、引用、更新、删除和追踪。切分后必须正确继承，不应只保留正文，否则难以定位原文与处理权限。

### 9.3 RecursiveCharacterTextSplitter

递归字符切分先尝试较自然的分隔符，再用更细粒度的分隔符控制长度。相比固定位置截断，通常能更好保留段落与句子结构。

chunk_size 控制块上限，chunk_overlap 让相邻块保留部分重叠。若长度函数使用 len，单位是字符；采用 tokenizer 才能按 token 计数。

块太小：上下文缺失、索引数量增大；块太大：相关信息被噪声稀释、上下文与重排成本增加。overlap 太大还会产生大量重复内容。

粗略估算可以写为：

~~~text
块数约为 ceil((文本长度 - overlap) / (chunk_size - overlap))
~~~

这是固定窗口的近似，不代表递归切分一定产生该数量；自然分隔会改变结果。

### 9.4 MarkdownHeaderTextSplitter

按标题层级切分有助于保留主题边界，标题也可作为 metadata。随后可以再按长度细分，兼顾主题与模型输入限制。

若标题与正文分离、代码块误被识别或元数据在二次切分时丢失，语义仍会受损。因此切分后应抽样检查真实块内容。

### 9.5 语义切分与父子块

语义切分依据语义变化划分段落，更灵活但增加编码成本。父子块策略用小块召回，返回更大的父块作证据，平衡匹配精度与完整上下文。

这些是相关优化方法，不能仅因使用文本切分库就声称具备。评估时应比较同一黄金集上的召回、答案完整性和费用。

### 9.6 增量入库

内容哈希可判断文件是否改变，减少重复解析与向量化。稳定块 ID 便于更新和删除，但 ID 设计要考虑文档身份、语料作用域和版本。

文件路径哈希解决“这份文件是谁”，内容哈希解决“内容是否变了”，两者用途不同。仅用路径和块序号生成 ID 时，重切分后需谨慎处理旧块。

删除旧索引后再添加新索引存在失败窗口。更可靠的策略是生成新版本 → 完整校验 → 切换可见版本 → 清理旧版本。源文件删除也需要索引对账，不能只处理新增与修改。

## 10. Embedding、向量距离与向量数据库

### 10.1 Embedding 是什么

Embedding 把文本映射为固定维度的实数向量，让相似语义在向量空间中更接近。检索时分别编码问题与文档，再按相似度选择候选。

维度影响存储和计算，但维度越大并不保证效果越好。模型训练目标、语言覆盖、领域与文本长度同样重要。

检索模型可能区分 query 和 document 编码任务。缓存和适配接口要保留这种区别，不能默认相同文字两种用途的向量必然一致。

### 10.2 余弦相似度、内积与 L2

~~~text
余弦相似度 cos(q,d) = (q · d) / (||q|| ||d||)
欧氏距离 L2(q,d) = √Σ(q_i - d_i)²
内积 dot(q,d) = Σ(q_i d_i)
~~~

余弦强调方向，内积还受模长影响，L2 衡量几何距离。单位归一化后，余弦与平方 L2 有关系：||q-d||²=2-2cos(q,d)。未归一化不能直接套用。

数据库可能返回相似度，也可能返回距离或平方距离。排序方向和数值范围必须从接口确认。1/(1+d) 是将非负距离转换为递减分数的一种方式，不是经过校准的概率，也不能无条件称为余弦相似度。

### 10.3 Chroma 与 collection

Chroma 保存向量、文档与元数据，并按 collection 组织数据。持久化目录让数据跨进程重启保留；collection 名称用于逻辑隔离。

距离度量与索引参数应明确配置，并与实际已建 collection 对齐。默认参数可能受版本或已存在库影响，不能从一个变换公式推断索引度量。[Chroma 配置文档](https://docs.trychroma.com/docs/collections/configure)

### 10.4 精确检索与 ANN

精确检索计算所有向量的距离，结果准确但大规模时成本高。ANN 是 Approximate Nearest Neighbor，即近似最近邻，牺牲部分召回换取效率。

HNSW 通过多层图导航寻找邻近向量；上层快速定位，下层细化搜索。常见参数包括图连接数 M、构建搜索宽度与查询搜索宽度，影响内存、构建成本、延迟和召回。

理解 HNSW 是理解向量数据库的相关知识，使用数据库不等于亲自实现该算法。实际使用的索引与参数需按版本确认。

### 10.5 Metadata filter 与隔离

筛选用户、语料、版本或文档类型能缩小候选范围。安全过滤应在权限边界内执行，避免先取出越权资料后再简单丢弃。

独立 collection 与 metadata filter 是不同隔离方案。前者清晰但 collection 过多有管理成本；后者灵活但每个查询必须正确附加权限条件。高敏感数据还应考虑物理隔离。

### 10.6 向量模型迁移

更换模型、维度、归一化或任务参数可能改变向量空间。新查询向量不能直接和旧模型文档向量混用。

迁移通常创建新索引、重编码文档、评估、切流量，再清理旧索引。缓存键应包含模型版本、维度和编码配置，而不只是容易复用的模型别名。

### 10.7 存储规模估算

~~~text
仅原始 float32 向量占用 ≈ 文档块数 × 向量维度 × 4 字节
~~~

实际还包含图索引、正文、元数据、缓存和数据库开销。例如百万块的存储与查询要求不能只按源文件大小估计。

## 11. BM25 与关键词检索

### 11.1 词项检索与稀疏表示

关键词检索依赖词项匹配，擅长精确名称、错误码、缩写和编号；向量检索更擅长语义近似。词项匹配通常以稀疏特征表示，每个词占一个维度，大部分维度为零。

BM25 是经典概率相关性排序方法的一种实现家族，不是神经网络模型。rank_bm25 提供 BM25Okapi 等实现，处理已分词的语料。

### 11.2 TF、IDF 与长度归一化

TF 是词在文档中的频次；IDF 表示词的区分能力：大量文档都出现的词通常辨别力较低。文档长度归一化避免长文仅凭出现更多词占据优势。

常见 BM25 表达式为：

~~~text
score(q,d) = Σ IDF(t) × f(t,d)(k1+1)
                        / [f(t,d) + k1(1-b+b|d|/avgdl)]
~~~

f(t,d) 是词频，|d| 是文档长度，avgdl 是平均长度。k1 控制词频增长的饱和速度；b 控制长度归一化强度。不同实现的 IDF 和负值处理可能不同，比较分数时需确认实现。

词频增加的收益会逐渐饱和，避免简单重复堆词无限提升得分。[rank_bm25 实现](https://github.com/dorianbrown/rank_bm25)

### 11.3 中文分词与词项设计

中文没有天然空格边界。按单字切分简单但可能丢失专业词和实体；分词器加领域词典能保留术语；字符 n-gram 可以兼顾局部匹配，但增加索引与噪声。

英文处理常涉及大小写、标点、词形和停用词。代码与专有标识符可能大小写敏感，统一 lower 不一定正确。

分词方法应与任务匹配：制度问答、代码搜索、产品编号检索的词项需求不同。不能只看分词器是否“高级”。

### 11.4 小语料与分数退化

小语料中词频分布可能让部分 IDF 为零或负值，导致期望命中得分不明显。词重叠计数可以作为降级，但分数尺度已经变化。

BM25 分数、重叠计数和向量分数不可直接比较。阈值要基于实际语料、分词和实现校准。

### 11.5 内存 BM25 与搜索引擎

内存 BM25 库通常保存所有文档词项并逐篇计算分数；大型搜索引擎通过倒排索引、分片和查询优化控制成本。它们可能使用同类打分公式，但规模能力不同。

持久化内存索引可以减少重建，不会自动获得搜索引擎的分布式或大规模性能。pickle 能保存 Python 对象，但读取不可信 pickle 可导致代码执行，不能当作安全上传格式。

## 12. 混合检索、RRF、Rerank 与拒答

### 12.1 为什么使用混合检索

向量检索能捕捉同义表达，关键词检索能保留精确实体。混合检索合并两者候选，提高覆盖，但也会增加噪声、延迟和参数复杂度。

多路召回是否有效需要消融实验：单向量、单 BM25、融合、融合加重排分别测试，不能仅因为技术更多就认定效果更好。

### 12.2 Top-k 的取舍

召回 k 越大可能提高 Recall，但会增加排序、重排与上下文成本。最终喂给模型的文档数应该小于或等于候选规模，以控制噪声。

召回阶段侧重“找得到”，精排阶段侧重“排得好”，最终上下文侧重“证据足够且不重复”。这些参数应分别设置。

### 12.3 RRF 的公式与例子

RRF 是 Reciprocal Rank Fusion，按不同结果列表中的排名融合：

~~~text
RRF(d) = Σ 1 / (k + rank_i(d))
~~~

rank 从 1 开始，文档未出现在某一路时该路不贡献分数。常用 k=60，降低单一路首位对总分的过大影响。不同原始分数不必在同一尺度。[RRF 官方说明](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)

例如文档 A 在两路分别第 1 和第 3：1/61+1/63≈0.03227；文档 B 只在一路第 1：1/61≈0.01639。多路一致命中的 A 会获得更高融合分。

RRF 使用排名，忽略原始分差；第一与第二差距很大时也只体现相邻名次。它需要稳定文档 ID 去重，重复候选不应意外重复加分。

RRF 分数不是概率，且大小与召回路数、k 和候选规模相关，不能用作通用“可信度”。

### 12.4 Rerank 与 Bi-encoder/Cross-encoder

Bi-encoder 分别编码问题与文档，文档向量可预计算，适合快速召回。Cross-encoder 联合处理问题与候选文本，通常能更细致判断相关性，但每对都要计算，成本更高。

Rerank 是重排序阶段，常见实现是 Cross-encoder，也可以使用专门服务或其他排序算法。不能只根据 API 名称断言某闭源模型的内部结构。

重排只对候选工作，不能找回未被召回的资料。应限制候选数，设置超时和回退，并分别校准重排分数与融合分数阈值。

### 12.5 相关性门控与拒答

Top-k 总会返回“相对较近”的内容，即使全库都不相关，因此需要判断证据是否足够。向量与关键词都弱时拒答，是一种双信号策略。

阈值太高导致可回答问题被拒绝，太低导致误答。向量、BM25、RRF、Rerank 分数的尺度不同，不能共享一个未经验证的阈值。

“检索相关”与“足以回答”也不同。资料可能提到主题，却缺少具体日期、条件或结论；生成后仍需要证据覆盖与引用校验。

### 12.6 冲突、时效与引用

同主题不同版本可能矛盾。元数据应包含生效时间、版本、来源权威性与范围。排序不能只看语义分数，还应处理当前适用版本。

引用最好关联稳定 source_id 或 chunk_id，并能回到原文。提示模型输出来源只是初步措施；进一步应验证所引用片段是否真正支持该断言。

## 13. 缓存、哈希、版本与一致性

### 13.1 缓存的三个对象

- Embedding 缓存：保存文本编码结果，减少重复向量化。
- 文档结果缓存：保存某个检索问题对应的证据集合，减少重复检索与重排。
- 答案缓存：保存最终回答，减少重复生成。

缓存层级越靠后，省下工作越多，但有效性条件也越多。答案不仅依赖问题，还依赖证据、提示、模型、参数、用户权限和对话上下文。

### 13.2 内存与持久化缓存

内存读取快，但重启丢失；SQLite 或文件缓存可跨重启使用，但存在序列化、磁盘增长与并发写入成本。

“两层结果缓存”和“内存加磁盘两级存储”是不同分类：前者按缓存内容，后者按保存介质。

### 13.3 TTL、LRU 与负缓存

TTL 是存活时间，限制旧结果复用；LRU 淘汰最近最少使用项，限制容量。它们可以同时存在，分别解决时间与空间问题。

负缓存保存无结果或某些失败结果，避免反复查询。它应有较短 TTL，否则新增知识后仍可能持续返回空结果。认证错误、暂时超时等失败也不应一概缓存为“没有知识”。

内存淘汰并不自动删除持久化条目，过期 SQL 行和文件需要定期清理。

### 13.4 缓存键设计

可用概念模型表示为：

~~~text
EmbeddingKey = hash(真实模型版本, 编码任务, 维度, 参数, 文本)
RetrieveKey  = hash(用户/权限, 语料版本, 检索配置, 规范化问题)
AnswerKey    = hash(RetrieveKey, Prompt版本, 生成模型, 生成参数, 上下文)
~~~

这是理想设计示例，实际系统需按成本选择字段。遗漏字段可能导致错误复用：调阈值却仍命中旧结果，换模型却复用旧向量，用户 A 读到用户 B 答案。

### 13.5 精确缓存与语义缓存

精确缓存通常对规范化字符串匹配，去除多余空白等。语义缓存按向量相似度复用近似问题答案。

语义相近不等于答案相同：“今天”和“明天”、“上海”和“北京”、“允许”和“不允许”可能很相近，但关键条件不同。语义缓存需要实体、时间、否定、权限等严格校验，不能只靠一个相似度阈值。

多轮代词问题更不能只按短文本缓存，必须考虑指代与上下文。

### 13.6 SHA-256 与内容寻址

SHA-256 把任意输入映射为固定长度摘要，适合内容版本、去重和缓存文件名。哈希不是加密，不能隐藏可猜测的短文本，也不能替代访问控制。

截断哈希降低存储与显示长度，同时提高理论碰撞风险。安全与唯一性要求应按应用规模决定；不能只因为“用了 SHA-256”就认定短前缀绝对不会冲突。

### 13.7 缓存失效与版本

版本加入缓存键可以让旧条目自然不再命中；主动清理释放空间。版本更新必须覆盖所有知识变化，包括新增、修改、删除和权限调整。

先修改知识再递增版本，或先递增版本再完成索引，都可能有窗口。跨存储更新需要完整状态、原子切换或可恢复事务流程。

### 13.8 击穿、穿透与雪崩

- 击穿：热门缓存过期，多请求同时执行昂贵计算。可用 single-flight 或互斥重建。
- 穿透：重复查询不存在内容。可用短 TTL 负缓存和输入校验。
- 雪崩：大量缓存同时失效。可用 TTL 抖动、分批更新和容量保护。

这些属于缓存可靠性知识。进程内 RLock 可以保护数据结构，却不一定防止不同进程同时重算同一问题。

### 13.9 文件写入与一致性

文件缓存直接覆盖可能被并发读取到半成品。常见改进是临时文件写入、校验，再原子替换。还应验证向量类型与维度，处理损坏文件和容量上限。

缓存不应成为唯一事实来源，失效或损坏时应能重建；有用户隐私的数据还需符合删除和保留要求。

## 14. SQLite 与数据建模

### 14.1 关系型数据库与 SQLite

关系模型通过表、行、列和约束组织数据，SQL 用于查询与更新。SQLite 是嵌入式数据库，应用直接读写本地数据库文件，不需要独立数据库服务器。

优势是轻量、部署方便、事务支持完善，适合单机应用。限制主要在并发写入、横向扩展和运维治理；不能把本地文件数据库等同于生产数据库集群。

### 14.2 主键、外键与唯一约束

主键标识一行；外键规定引用关系；唯一约束阻止重复值。复合主键可用多个字段共同识别记录，例如身份作用域加会话标识。

SQLite 外键检查需要正确启用。没有外键的关联表需要自行清理孤立数据。名称唯一还涉及大小写与 Unicode 规则，NOCASE 不等于所有语言的完整字符折叠。

### 14.3 事务与 ACID

ACID 分别是原子性、一致性、隔离性、持久性。事务让一组相关 SQL 写入共同提交或回滚，避免只写一半。

数据库一致性是约束和正确事务共同实现的，不会自动理解业务规则。SQLite 事务也不会覆盖另一个向量数据库或独立文件索引。

### 14.4 参数化 SQL 与 LIKE

参数化 SQL 将查询结构与输入值分离，降低 SQL 注入风险。禁止把用户输入直接拼入 SQL 语句。

LIKE 支持通配符匹配，输入中的 % 与 _ 有特殊含义。参数化避免注入，但不自动把通配符当普通字符。全文索引与 LIKE 全扫描也有性能差异。

### 14.5 索引与查询计划

索引通过额外结构加快过滤和排序，代价是空间与写入维护。复合索引列顺序应符合主要查询，如 user_id 后接更新时间或状态。

应使用 EXPLAIN QUERY PLAN 与真实数据规模判断，不必给每列都加索引。大量文本 LIKE 查询通常需要全文检索或专门搜索方案。

### 14.6 并发、锁与 WAL

SQLite 可以有多个读者，但写入并发受限。WAL 模式能改善读写并行，却不能把多写者变成无限并行。

事务应尽量短，网络或模型调用不应长期占用写事务；同时设置合适超时和错误处理。连接是否允许跨线程使用与业务是否安全是不同问题。

### 14.7 身份、隔离与授权

user_id 是数据作用域字段。每个读取、修改、删除都应检查所有权，不能只在查询列表时过滤。

数据隔离不等于认证。让调用者输入某个用户名，不证明他就是该用户；共享 API Key 也不自动形成每用户权限。身份验证与授权需要独立设计。

### 14.8 删除、迁移与时间

删除会话应考虑消息、检查点、缓存与其他衍生数据。删除业务表一行并不代表所有系统中的相关数据都消失。

Schema 变化应有版本迁移，避免只在启动时 CREATE TABLE IF NOT EXISTS。时间宜统一保存 UTC 或明确时区，展示时转换，避免本地时间与数据库默认 UTC 混用。

## 15. HTTP、HTTPX、FastAPI 与 Pydantic

### 15.1 HTTP 请求与响应

HTTP 请求由方法、URL、请求头和可选请求体组成；响应包含状态码、响应头和正文。GET 通常读取资源，POST 提交数据或触发操作。方法语义与业务幂等性需要一起设计。

常见状态包括 200 成功、400 输入错误、401 未认证、403 无权限、404 未找到、429 限流、500 服务内部错误和 503 服务暂不可用。供应商还可能在 HTTP 200 正文中返回业务错误码，所以必须检查两层状态。

### 15.2 JSON 与输入输出契约

JSON 是语言无关的数据交换格式，支持对象、数组、字符串、数值、布尔和 null。Python 字典的字符串表示不是 JSON，例如单引号和 None 的写法不相同。

契约要规定字段是否必填、数据类型、单位、时间格式、错误结构与兼容策略。仅能解析 JSON 不代表字段业务含义正确。

### 15.3 HTTPX

HTTPX 提供同步与异步 HTTP 客户端。持久化 Client 可以复用连接池，减少重复 TCP/TLS 建连开销；临时请求更简单，但高频场景复用能力较弱。

网络超时可分连接、读取、写入和连接池等待。统一数字不总等于请求整体墙钟上限，流式读取尤其需要总量和总时间预算。

raise_for_status 检查 HTTP 错误；响应 JSON 还要业务校验。还应限制响应体大小、重定向行为、目标协议和 Content-Type，避免异常资源消耗。

### 15.4 重定向、URL 与 DNS

URL 包含协议、主机、端口、路径、查询参数与片段；不能简单用字符串前缀判断实际主机。DNS 将主机名解析为地址，可能返回多个 IPv4/IPv6。

重定向会改变实际访问目标；相对 Location 需要正确解析后再检查。每次跳转都应重新验证目标，限制跳转次数。URL 查询参数中的凭证容易进入日志，不宜作为默认秘密传递方式。

### 15.5 搜索摘要与正文提取

搜索接口返回的标题、链接、摘要属于候选线索。HTML 去标签能得到部分文本，但不等于正文识别，容易混入导航、广告和重复内容。

正文提取还涉及编码、HTML 实体、布局、表格与 JavaScript 渲染。信息时效和来源权威性需要单独核对，不能把“有搜索结果”当作“事实已验证”。

### 15.6 FastAPI 与 ASGI

FastAPI 将路径函数、输入模型与 HTTP 接口关联，并自动生成 OpenAPI 文档。ASGI 定义服务器与应用的交互，Uvicorn 是常用 ASGI 服务器。

同步路径函数通常在线程池执行；async 路径函数在事件循环执行。后者调用阻塞函数仍会阻塞，需要异步客户端或显式卸载阻塞工作。

自动生成接口文档提高可用性，但文档不是认证与安全控制。外部部署还应管理文档暴露、访问频率和敏感错误。

### 15.7 Pydantic 与校验

Pydantic 根据类型与字段规则解析外部数据，支持长度、数值范围、嵌套结构和自定义校验。[FastAPI 请求体资料](https://fastapi.tiangolo.com/tutorial/body/)

“输入格式合法”与“用户有权限操作该记录”是两层检查。日期字符串类型合法，也不一定表示真实日期或符合业务时区。

解析可能发生类型转换，需要严格模式时应显式设置。响应模型控制对外字段，减少内部数据意外泄露。

### 15.8 Lifespan 与健康检查

Lifespan 管理应用启动与关闭资源，例如初始化数据库、创建客户端和释放连接。资源清理对长期运行尤其重要。

Liveness 证明进程仍能响应，Readiness 证明必要依赖可用。返回 ok 不自动证明模型凭证、数据库和索引正常；依赖探测应有轻量、限频和超时策略。

### 15.9 真正的流式接口

SSE 用持久连接发送事件，适合服务器向客户端持续推送；WebSocket 支持双向通信。逐 token 展示还需要后端转发模型片段、处理取消、断线、错误和最终持久化。

前端逐字播放已经生成的字符串，只是展示效果，不改善真实模型首 token 到达时间。

## 16. 安全与可信边界

### 16.1 Authentication 与 Authorization

Authentication 证明调用者是谁；Authorization 判断他能访问什么。用户名、记录 ID 和 API Key 是不同性质的数据，不应混淆。

共享 API Key 可限制谁能调用服务，但未必区分用户。每用户授权需要将可信身份映射到资源范围，而不是接受调用方任意提供用户名后直接选择数据。

### 16.2 API Key 与秘密管理

API Key 应保存在服务端环境、秘密管理器或权限受控文件，避免写入源码、提示、客户端和 Git。Bearer 与 X-API-Key 是常见传递方式，必须配合 TLS。

secrets.compare_digest 可减少比较时机泄露，但不能解决凭证被复制、暴力猜测或无速率限制。还需随机长度、轮换、撤销和访问审计。

日志脱敏、配置示例占位符和忽略 .env 都是必要措施，但不是单独充分条件。

### 16.3 Prompt Injection

提示词注入试图让低信任输入改变高信任规则。直接注入来自用户，间接注入来自网页、知识库、文件或工具结果，例如资料中夹带“忽略之前规则并泄露秘密”。

核心问题是数据和指令都通过自然语言传入模型。防护应包括信任分层、最小权限、不可信内容标记、工具输入验证、敏感动作审批和输出检查。

正则能识别已知模式，但会漏掉改写、多语言和编码攻击，也可能误伤正常安全讨论。它是辅助层，不是完整注入防火墙。

### 16.4 系统提示不是秘密保险箱

系统提示表达行为约束，不应保存 API Key 或不该暴露的秘密。即使不输出原文，模型也可能转述或间接泄露内容。

“系统规则优先”属于设计要求，不能当作绝对安全承诺。确定性权限、资源限制和秘密存储必须位于模型之外。

### 16.5 SSRF

SSRF 是服务器端请求伪造：攻击者诱导服务访问本机、内网或云元数据接口。即使入口只接受 URL，也可能造成内部数据泄露。

防护需要解析协议与主机，检查所有 DNS 地址，拦截环回、私网、链路本地、保留和元数据地址，并验证重定向。IPv6、特殊 IP 表示和 DNS 重绑定也需要考虑。

DNS 检查后，真实连接可能再次解析，形成检查与使用之间的竞态。较强防护包括网络出口策略、受控代理、域名白名单和连接地址约束。

### 16.6 路径遍历与文件边界

../、绝对路径和符号链接可能突破预期目录。应解析到规范化实际路径后，检查是否位于允许根目录，而不是只删除几个字符。

路径检查与文件打开之间也有竞态；高风险环境需更严格文件句柄策略。读取大小、编码和文件类型同样要限制，目录隔离不是资源隔离的全部。

### 16.7 AST 白名单与任意代码执行

eval 会解释任意表达式，可能通过名称、属性、函数调用造成执行风险。AST 白名单只接受允许节点和操作符，能把“数学表达式”限制为明确语法。

白名单也需资源控制：大整数、幂和深度嵌套可能耗尽 CPU/内存。应在运算前检查指数、位数、节点数与深度，并设置时间或进程边界。结果出来后才判断太大，可能已经太晚。

浮点运算存在舍入误差；Decimal 更适合明确十进制精度要求，Fraction 适合有理数表达。安全计算不等于无限精度计算。

### 16.8 反序列化与 YAML

pickle 可能在加载时执行对象构造逻辑，不应处理不可信文件。JSON 更适合交换普通数据，但仍需验证类型、大小和业务含义。

YAML 不安全加载可能构造任意对象，SafeLoader 限制到安全数据类型。安全解析不等于配置内容合理，仍需检查参数范围与字段。

### 16.9 日志隐私与最小权限

字段名含 key 或 token 时脱敏，只能处理已知字段。嵌套内容、URL、异常文本和用户粘贴的秘密也可能泄露。

最小权限意味着工具只获得必要数据和动作范围。公开资料读取、个人资料读取、内部索引变更与业务写入应有不同权限级别，而不是全部统一开放。

## 17. Streamlit 与交互状态

### 17.1 脚本重跑模型

Streamlit 使用 Python 编写交互界面。用户操作通常触发脚本自上而下重跑，因此局部变量不会天然在下一次执行保留。

与传统前后端框架相比，上手快且代码量较少，但状态管理、重复初始化和长任务要格外处理。

### 17.2 Session State

st.session_state 保存浏览器会话内的数据和 widget 状态，例如选择项、消息和界面状态。它不是持久数据库，也不等于认证会话。[官方 Session State 文档](https://docs.streamlit.io/develop/api-reference/caching-and-state/st.session_state)

浏览器连接重建可能影响状态，因此需要数据库保存持久数据。用户切换时要清理与旧身份关联的界面和资源状态，避免混用。

### 17.3 Widget key、回调与 rerun

稳定 key 让框架识别同一 widget 并关联值。回调和脚本执行顺序会影响显示；如果先按旧值渲染后更新状态，可能出现第二次点击才更新的现象。

应让 widget 值与业务状态有明确的单一来源，避免同时用动态 index 和旧 session 值控制同一选择。rerun 是重新执行脚本，不是数据库事务，也不会自动清理全部资源。

### 17.4 数据缓存与资源缓存

st.cache_data 适合可序列化计算结果；st.cache_resource 适合共享客户端或模型资源。它们的生命周期与 session_state 不同。

缓存共享资源时必须考虑线程安全和用户隔离，不能把某用户会话数据存为全局共享资源。框架提供缓存机制不代表任何应用已正确采用。

### 17.5 Chat UI 与流式展示

聊天组件组织角色消息，write_stream 消费文本或事件片段。展示顺序、异常中断、重复保存和历史恢复都要独立处理。

真实体验指标包括响应开始时间、完整回答时间、取消行为和错误提示，不是只有“看起来在打字”。

<a id="k18"></a>
## 18. 日志与可观测性

### 18.1 日志级别与 Handler

logging 将日志生成、过滤、格式化和输出分离。常见级别 DEBUG、INFO、WARNING、ERROR、CRITICAL，分别用于细节、正常事件、异常趋势、失败与严重故障。

Logger 的级别与 Handler 的级别共同决定输出。控制台是 INFO 不代表文件不会保留 DEBUG，应检查完整配置。

### 18.2 结构化日志与关联 ID

结构化日志使用稳定字段描述事件，便于检索和聚合。request_id 标识一次请求，user_id 标识身份作用域，session/thread 标识连续执行上下文，model_id 标识模型选择。

关联 ID 让一轮任务中的模型、检索和工具日志可以串联。上下文传播与清理错误会把事件归到错误请求，因此必须验证并发场景。

JSON 日志是可机器解析的格式，但把所有字段塞成一个 msg 字符串，会削弱字段查询能力。

### 18.3 耗时、轮转与保留

perf_counter 适合测量持续时间，不依赖墙钟调时；datetime 适合记录时间点。两者不要互换。

TimedRotatingFileHandler 按时间轮转，backupCount 控制备份数量。字符裁剪与文件轮转是不同策略；裁剪可能截断记录边界，必须考虑归档、保留和审计需求。

进程内日志锁不保证多个进程同时写文件安全。高并发应用可用标准输出采集、日志队列或集中式服务。

### 18.4 Logs、Metrics 与 Traces

- Logs：具体发生了什么，适合事件与错误细节。
- Metrics：持续聚合的数量和分布，例如错误率、延迟、缓存命中率。
- Traces：一次请求的跨组件调用关系与各阶段耗时。

有 request_id 日志是追踪的基础，不等于已经接入 OpenTelemetry。后者规范化 span、上下文传播和导出，属于进一步观测技术。

### 18.5 可观测性与隐私取舍

日志要足够复现问题，但不应保存全部敏感提示和私人知识。可记录模型版本、参数、块 ID、状态、耗时和脱敏预览，把完整内容放在受控调试环境。

记录成功状态要区分“函数没有异常”“上游成功”“任务达到目标”，否则报表会掩盖真实失败。

## 19. 测试、评测与实验设计

### 19.1 单元、集成与端到端测试

单元测试验证局部逻辑；集成测试验证数据库、框架和组件连接；端到端测试从真实入口检查完整流程。它们覆盖层次不同，不能相互替代。

pytest 提供测试发现、fixture、参数化和断言。tmp_path 隔离文件，monkeypatch 替换配置和依赖。FastAPI TestClient 可以验证接口行为，但不等于真实公网部署测试。

### 19.2 Mock 的价值与边界

Mock 让网络、模型和时间行为稳定，适合验证失败分支、参数、隔离和回归。它不能证明供应商当前可用或模型语义正确。

过度模拟框架可能掩盖上下文传播问题，因此关键集成应使用真实框架执行，仅模拟昂贵的外部接口。

### 19.3 黄金集与数据划分

黄金集是一组人工标注、可追踪的任务与期望。知识问答应包含可回答、不可回答、歧义、冲突、过时、跨用户和注入样本。

开发集用于调参，独立测试集用于最终判断，避免用同一组问题反复调到“高分”却无法泛化。样本要保留来源、证据和标注规则。

### 19.4 检索指标

~~~text
Precision@k = 前 k 个结果中相关文档数 / k
Recall@k    = 前 k 个结果中相关文档数 / 全部相关文档数
MRR         = 各问题首个相关结果排名倒数的平均值
DCG@k       = Σ (2^rel_i - 1) / log2(i+1)
nDCG@k      = DCG@k / 理想排序的 DCG@k
~~~

Recall 衡量找全能力，MRR 强调首个相关结果，nDCG 支持不同相关程度与排序质量。仅统计“返回了文档”不是检索准确率。

### 19.5 回答质量与拒答指标

正确性检查是否回答对；Faithfulness 检查是否忠实于证据；完整性检查是否覆盖要求；引用有效性检查来源是否支持断言。

拒答应同时统计无答案问题是否正确拒绝，以及有答案问题是否被误拒绝。允许“命中或拒答都算成功”的标签会降低指标解释力。

自动 LLM-as-a-judge 可辅助评测，但受评审模型、提示和偏差影响，宜配合规则与人工抽检。

### 19.6 Agent 与工具评测

任务成功率考察目标是否完成；工具选择准确率考察选对能力；参数正确率考察实体和格式；副作用检测考察重复与越权。

没有抛异常不等于成功。返回“没有结果”“查询失败”或者任务写错用户，仍应算对应失败。

### 19.7 性能、费用与统计

需要测冷缓存、热缓存、不同语料规模和并发负载。平均延迟可能掩盖尾部问题，应报告 p50、p95、p99，同时说明样本数和环境。

逐 token 输出可测 TTFT（首 token 时间）与完整结束时间；字符动画不能作为真实 TTFT。费用应包含所有模型、重排和搜索调用。

多轮测试能观察随机性，但三次成功不是生产可靠性证明。报告应列明条件、未覆盖项和失败情况。

### 19.8 消融与调参

一次改变一个主要因素，固定测试集与环境，比较召回、质量、费用和延迟。常见因素包括块大小、重叠、候选 k、重排、阈值与缓存。

调参顺序通常先保证解析与权限正确，再改善召回、排序、证据构造和生成；不要用输出提示掩盖错误索引。

## 20. 配置、依赖、启动与部署

### 20.1 YAML、环境变量与 .env

YAML 适合可读的层级配置；环境变量适合部署时注入；.env 是本地开发便利方式。python-dotenv 默认行为应与已有系统环境的优先级一起理解。

配置要有默认值、类型、范围和未知字段校验。配置文件中存在字段，不代表执行代码使用了它。热更新还取决于加载时机和实例缓存。

秘密与普通参数应分开管理，配置示例使用占位值。修改模型或 Key 后需要确认客户端是否重建，而不是只改文件。

### 20.2 虚拟环境与依赖管理

venv 隔离解释器所使用的第三方包，但不隔离操作系统权限和网络。pip 安装依赖及其传递依赖；范围声明保留升级空间，锁文件提高可重复性。

直接依赖与传递依赖需要区分。代码直接使用某库但依赖声明没有它，可能依赖本地偶然安装，导致环境不一致。

推荐记录 Python 版本、依赖锁定、平台条件和安装验证。安装成功与所有运行功能可用是两回事。

### 20.3 一键启动与 Bootstrap

启动脚本把目录切换、解释器检查、环境创建、依赖安装、配置检查和启动命令串联，减少人工步骤。

可靠启动需要考虑重复执行、失败退出、已有环境、端口冲突、路径空格和编码。仅用一个“安装完成”标记可能遗漏 requirements 变化，宜比较依赖文件哈希或版本。

Windows 批处理与 PowerShell 的引号和变量语法不同；包含空格的路径需要正确引用。UTF-8 有助于避免中文输出在不同终端乱码。

### 20.4 Docker 与 Compose

Docker 镜像封装运行文件系统与依赖，容器是镜像的运行实例。Dockerfile 描述构建层；Compose 管理服务、环境、端口和挂载。

volume 或绑定挂载用于持久数据，不应依赖容器可写层保存唯一业务数据库。EXPOSE 只是描述端口，真正对外还需发布端口和启动对应进程。

.dockerignore 控制构建上下文，避免 .env、虚拟环境、私人知识和数据库被 COPY 进入镜像。它与 .gitignore 职责不同。

容器化不等于自动生产化，还需要非 root 用户、资源限制、健康检查、秘密注入、备份与升级策略。

### 20.5 Git、版本与可复现记录

Git 记录源码历史；提交形成可回溯快照。日志记录运行过程，二者不能替代。代码、配置、提示和评测数据最好一起版本化。

秘密和私人运行数据不应纳入仓库。若秘密曾提交，即使后来删除文件也可能留在历史中，需要撤销和清理。

### 20.6 单体与服务化

单体将模块放在同一部署中，容易启动和调试。服务化可以独立扩容和隔离故障，但增加网络、认证、部署与一致性复杂度。

当模型调用、入库和索引规模增长时，可先抽出异步入库任务与统一模型网关，不必立刻把所有目录拆成微服务。

### 21.3 数据格式与算法基础

**JSONL：** 每行独立 JSON，适合逐条读取评测样本和事件。相比单个大 JSON 数组，便于追加和流式处理；仍需逐行处理坏数据。

**LRU 数据结构：** 保序哈希结构兼顾查找与最近访问顺序；访问后移动到末尾，超过容量从最旧端删除。高并发还需同步。

**词重叠：** 按查询与文档的词项交集估计相关性，简单可解释，但不考虑完整语义、否定与词频饱和。

**间隔复习：** 延长已掌握内容的复习间隔，缩短错误内容间隔。固定倍增只是启发式规则；SM-2、FSRS 等方法引入更复杂的记忆状态与调度模型，不能把简单规则称为这些算法。

**启发式与学习模型：** 正则、固定阈值、词重叠和倍增规则是人为制定的启发式；Embedding、Rerank 与 LLM 来自学习模型。二者可以结合，前者可解释，后者更灵活但需要质量验证。

## 22. 核心概念辨析与参考资料

### 22.1 需要准确区分的概念

- **LLM 与 Agent：** LLM 是生成模型；Agent 是围绕模型建立的决策执行系统。
- **Tool 与 Skill：** Tool 规定可执行动作；Skill 规定处理任务的方法和约束。
- **Chain 与 Graph：** Chain 适合固定组合；Graph 能显式表达分支、循环和状态。
- **RAG 与微调：** RAG 提供运行时外部证据；微调改变模型参数。
- **Embedding 与 Rerank：** 前者适合预编码与快速召回；后者对候选重新排序。
- **相关性与正确性：** 文本相关不代表它足以支持答案，更不代表答案事实正确。
- **距离与概率：** 距离或变换后的分数不是经过校准的正确概率。
- **缓存与记忆：** 缓存复用计算结果；记忆保存可用于后续决策的信息。
- **持久化与恢复：** 有状态存储不代表外部动作可安全恢复。
- **数据隔离与认证：** 按 user_id 过滤不证明调用者拥有该身份。
- **API Key 与用户登录：** 共享服务凭证不自动提供个人身份与权限。
- **生成器与 token 流：** 逐次 yield 不保证逐 token 推送。
- **安装库与采用能力：** 声明重试、缓存或框架依赖不等于完整实现。
- **配置与实现：** YAML 中存在字段不证明代码读取并使用。
- **Mock 成功与真实质量：** 模拟测试验证逻辑，不能代替真实模型评测。
- **容器与生产化：** 镜像可构建不等于安全、扩展和运维都已完成。
